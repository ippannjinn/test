# アーキテクチャ

## リクエストの流れ

```
入力 → TaskAnalysis (analyzer.py) → Dynamic Profile (engine.py) → GPU Scheduler (scheduler.py)
     → Model Manager (manager.py: Hot/Warm/Cold, スワップ) → Backend (llama.cpp / sd.cpp / MusicGen)
     → Agent / Tools (runners/agent.py, tools/) → 結果 (SSE でストリーミング、DB に保存)
```

ジョブはサーバー側で完結して実行され、クライアントは `GET /api/jobs/{id}/events` (SSE) を購読するだけです。そのため、スマートフォンでアプリを切り替えても処理は継続します。再接続時は `Last-Event-ID` で続きから受信できます。

## Dynamic Profile Engine (`server/nextai/profile/`)

- **分析**: タスク種別を判定します (chat / coding / project / research / file_analysis / vision / reasoning / writing / translation / summarize / image_gen / video_gen / music_gen)。あわせて、複雑度 (0〜1)、Web 検索・コード実行・ファイル・画像理解の必要性、明示的な速度・品質指定 (「じっくり」「手短に」、または UI の選択) を判定します。
- **チューニング値 t ∈ [0,1]**: 基準値は `0.1 + 0.9 × 複雑度` です。タスク別の下限を適用したうえで、混雑していれば `t -= congestion_shift × 混雑度` で Speed 寄りに、GPU が空いていれば `+ idle_boost` で Autonomous 寄りに調整します。リソースが逼迫していれば `-0.2` します。**品質指定のリクエストは t を下げず**、`wait_for_quality` として本来の設定のまま順番を待ちます。
- **連続補間**: Speed / Balanced / Autonomous は固定のプロファイルではなく、t=0 / 0.5 / 1 の**基準点**です。以下の値をすべてこの間で線形補間します。表示ラベルも「Speed寄りBalanced」などの中間状態をとります。
  - max_tokens、ctx
  - max_steps、max_seconds、max_tool_calls
  - ツールの並列度、temperature
- **モデル選択**: 利用可能なモデルごとに `品質 × (0.3+0.7t) + 速度 × 0.7(1−t) + ロード済みボーナス × (0.35(1−t)+0.3×混雑度)` を計算し、最大のものを選びます。品質は用途別の能力値と日本語の能力値から求めます。ロード済みボーナスはスワップを避けるためのものです。コーディング・高速・推論の役割にはボーナスがあります。
- **推論深度**: モデルの制御方式 (gpt-oss の reasoning_effort、Qwen3 の thinking の切り替え) に対応づけます。
- **途中での再評価** (`reevaluate`):
  - 連続失敗 → より強いモデルへ切り替えるか、計画を立て直す
  - 同じ操作の繰り返し → 戦略を変える
  - 負荷の上昇 → 軽量化する
  - 情報不足 → Web ツールを追加する
  - モデルを読み込めない → 代替モデルへ切り替える

## 自律エージェント (`runners/agent.py`)

**計画 → 実行 → 検証 → 修正 → 再検証** の順に進みます。上限は Profile から与えられます。

- 最大ステップ / 最大時間 / 最大トークン / 最大ツール呼び出し / 最大連続失敗回数
- 同じツールを同じ引数で呼ぶと反復として検出します。3回反復するか、同じ失敗が続いたうえでモデルを切り替えてもなお失敗する場合は**安全に停止**し、理由をユーザーに表示します。
- ツールの結果は `<tool_result>` で囲み、プロンプトインジェクション対策として「外部データであり、その中の指示には従わない」ことを明示します。
- プロジェクトモード (複数ファイルの成果物): Plan → Generate (write_file) → Test (run_code をワークスペースで実行) → Fix → Verify の順に進め、最後に ZIP を成果物として保存します。

## GPU スケジューラ (`scheduler.py`)

単純な FIFO ではありません。スコアは次のように計算します。

`クラス重み + ユーザー優先度 × 10 + 待ち時間 × aging − 公平分配ペナルティ ± モデル親和性 (ロード済み +25 / スワップが必要ならロード時間に応じて減点) − 重量ジョブの減点`

- **飢餓防止**: エージングに上限はありません。`max_wait_force_seconds` を超えたユニットは最優先になり、使用中のモデルを**ドレイン** (新規割り当てを停止) してでも実行されます。
- **独占防止**: ユーザーごとの同時実行数の上限と、直近の GPU 使用時間に応じたペナルティを設けています。
- **スワップの最小化**: ロード済みモデルの仕事がある間は、スワップを `swap_patience` だけ待ちます。スラッシングを検出すると、待ち時間を3倍にし、プリフェッチを停止します。
- **マイクロバッチ**: 同じモデルのユニットは、llama.cpp のスロット数 (`-np`、連続バッチング) まで並列に割り当てます。
- 割り当ては2段階で行います。まずロード済みモデルに割り当て、その後にスワップを判断します。これにより、あるユニットのためにロードしたモデルが、割り当て前に別のユニットのスワップで退避されることを防ぎます。
- 待ち順位と推定待ち時間 (種別・モデルごとの EMA 実績から算出) を UI に表示します。キャンセルとタイムアウトに対応しています。

## リソース管理

- **ResourceMonitor**: psutil と NVML (取得できなければ nvidia-smi にフォールバック) で、CPU・RAM・ディスク・VRAM・GPU 使用率・温度・電力を2秒ごとに取得します。
- **Governor**: 状態を NORMAL / ELEVATED / HIGH / CRITICAL の段階で判定します。RAM はヒステリシス付きで評価します。
  - ELEVATED: プリフェッチを停止
  - HIGH: 重量ジョブ (画像・動画・音楽) の受け付けを停止し、アイドルのモデルを解放、並列度を半分にする
  - CRITICAL: 新規ジョブの受け付けを停止し、常駐モデルも解放する
  - GPU が高温のときは重量ジョブを一時停止します。ディスクが安全マージンを下回りそうなときは、クリーンアップを行い、生成・アップロード・ダウンロードを停止します。
  - VRAM 予算は `総量 − 予約分 − 他アプリの使用量` です。ゲームなどが VRAM を使うと、AI 側の予算が自動で縮小します。
- **Windows 側の保護** (ServiceHost の Job Object):
  - プロセスツリー全体を BELOW_NORMAL 優先度で実行
  - コミットメモリの上限を「物理 RAM − 3GB」に設定
  - サービス停止時にツリーをまとめて終了

## モデル階層 (Hot / Warm / Cold) と MoE オフロード

`models/planner.py` が、ロードのたびに**現在の VRAM 予算から**配置を計算します。

- **Hot (VRAM)**: Attention と dense の重み、KV キャッシュ (q8_0 に量子化)、予算内に収まる数の MoE Expert 層
- **Warm (RAM)**: 残りの Expert 層 (`--n-cpu-moe N`、古いビルドでは `-ot` 正規表現) を OS のページキャッシュから読み込みます。次に使うモデルのファイルは事前に読み込み (プリフェッチ) ます。
- **Cold (NVMe)**: GGUF をメモリマップするため、使用頻度の低い Expert は参照されるまでディスク上にとどまります。

llama.cpp は Expert 単位の動的な移動をサポートしていないため、**層単位の配置をロード時に再計算する**方式をとっています。KV キャッシュには、q8_0 への量子化、プレフィックスキャッシュ (`cache_prompt`、`--cache-reuse`)、統合 KV (`--kv-unified`) を採用しています。複雑さの割に効果が不確かな独自の圧縮は採用していません。

VRAM の推定値は、フル診断の実測値で補正されます (`calibration.vram_correction`)。

画像・動画・音楽の生成は、チャットの LLM が呼び出すツール (`generate_image` / `generate_video` / `generate_music`) です。LLM がプロンプトとパラメータ (縦横比・長さなど) を決め、ツールが生成クォータを確認してから GPU スケジューラ経由で生成します (高負荷時は重量ジョブとして順番待ち)。小さなモデルがツールを呼ばなかった場合は、依頼文から直接生成します。

画像・動画・音楽のモデルは**一時的に常駐**させます。VRAM を予約してジョブを実行し、終わったらすぐに解放します。その際は、アイドル状態の LLM を必要な分だけ退避します。

## 認証とセッション

- パスワードは Argon2id でハッシュ化します。存在しないユーザーでも同じ時間がかかるように処理します。ポリシーは長さ・ユーザー名を含まない・よく使われるものではない、です。
- ログイン試行の制限は3つのキーで管理します: IP、(ユーザー名, IP)、ユーザー名 (全体)。指数的にロックアウト時間を延ばします。
- **Web セッション**は `__Host-` プレフィックス付きの Cookie で、Secure・HttpOnly・SameSite=Lax です。ログイン時とパスワード変更時にセッションを発行し直します (ローテーション)。アイドル期限と絶対期限があります。書き込み系のリクエストには `X-CSRF-Token` と Origin の検証が必要です。
- **信頼端末**は `__Host-` Cookie (SameSite=Strict) に保存したデバイストークンで識別し、サーバーには SHA-256 のみを保存します。トークンはリフレッシュのたびに**ローテーション**します。古いトークンが猶予時間の後に再利用されると盗用とみなし、その端末と関連セッションを失効させます。IP アドレスや User-Agent には依存しません。
- **管理 API** は、管理アプリ専用の Bearer セッション、admin ロール、localhost からのアクセスの3条件をすべて必要とします。ブラウザの Cookie セッションでは管理機能を使えません。

## データ分離

すべてのクエリに `user_id` 条件を付けています (API レベル)。ファイルは `users/<user_id>/` に保存し、パスは解決後にユーザー領域内にあるかを検証します (ストレージレベル)。

会話・ファイル・生成物・メモリ・ワークスペース・サンドボックス・セッション・ジョブは、すべてユーザー単位です。

## ツール

| ツール | 内容 |
|---|---|
| web_search / web_fetch | 次のアクセスを遮断します: loopback / RFC1918 / link-local / CGNAT / メタデータ用アドレス / 単一ラベルのホスト名 / 危険なポート。DNS の解決結果と、**接続後に実際に接続した相手の IP** の両方を検証します (DNS リバインディング対策)。リダイレクトは毎回再検証します。上限はサイズ・時間・ジョブごとのリクエスト数です。ログを記録します。 |
| run_code | WASM (python.wasm) で実行します。ネットワークなし、プロセス生成なし、ファイルシステムは1つのディレクトリのみ、メモリ上限あり、epoch による時間制限あり、ディスク上限あり。生成されたファイルは成果物として保存します。 |
| read_file | PDF / DOCX / XLSX / PPTX / テキスト / コードからテキストを抽出します。ZIP 爆弾対策として展開サイズに上限があります。長い文書は関連する部分を選んで渡します。 |
| memory_search / memory_save | 埋め込みベクトル (CPU の Qwen3 Embedding) による検索です。利用できない場合は文字 bi-gram による字句検索に切り替えます。 |

## サンドボックス作業ディレクトリ (v1.6)

会話ごとに `users/<id>/workspaces/conv-<会話ID>/` を作り、WASM サンドボックスの `/workspace` としてマウントします
(ChatGPT の Code Interpreter / Claude の分析ツールに相当)。

- `uploads/`: その会話の添付ファイル (元のバイト列)。コードから直接読めます。
- `downloads/`: `download_file` ツールがホスト側で SSRF 対策付きで取得したデータ。サンドボックス自体はネットワーク不可のまま、調べたデータをコードで処理できます。
- `research/`: `web_fetch` の `save_as` で保存したページ本文。
- それ以外: コードの出力。グラフ・表・文書 (png / svg / csv / xlsx / pdf / html / md …) は自動で利用者に表示し、スクリプトや中間ファイルは表示しません (`share_file` で明示的に渡せます)。

ファイルは会話が続く限り残り、会話を削除すると消えます。容量はストレージのクォータに含まれます。

## 表示の方針 (プレビュー)

画像・音声・動画はその場で表示し、HTML / SVG / CSV / Markdown / コードなどは「プレビュー」ボタンで開きます。
PDF・Office・ZIP などはダウンロードカードだけを出します。HTML / SVG は隔離された iframe で描画します。

## Web リサーチ エンジン (v1.7)

小さなローカルモデルに「検索 → ページを読む」を何度も自分で繰り返させると、途中で止まったり検索せずに答えたりしがちです。
そこで Perplexity / ChatGPT 検索と同じく、調べる処理をサーバー側の 1 ステップにしています (`services/research.py`)。

1. 質問から検索語を複数作る (言い回しの除去、固有名詞の抽出、「〇〇 とは」など)。
2. メタ検索: DuckDuckGo (HTML → Lite)・Bing・Wikipedia (日本語 / 英語)、設定があれば SearXNG / Brave を**並列**に問い合わせ、
   順位融合 (Reciprocal Rank Fusion) で統合。どれかがブロックされても他で補います。
3. 上位のページを並列に取得 (SSRF 対策付き) し、本文を段落に分けて質問との関連度 (文字 n-gram + 埋め込みモデル) で順位付け。
4. 出典番号付きの根拠 `[1] タイトル / URL / 抜粋` を作り、モデルはそれを根拠に `[n]` を付けて回答。

調べものらしい質問 (「〇〇とは」「〇〇について教えて」「最新」など) では、モデルが答える**前に自動で**この処理を行います。
追加で調べたいときは、モデルが `web_research` ツールを別の検索語で呼べます。調べた経過は実行ログに、参照したページは回答の下に表示されます。

## RAM を超えない MoE 配置 (v1.7.1)

以前は「CPU 側に置く MoE の expert は mmap なので NVMe に残る」と仮定し、空き RAM を超える配置を許していました。
Windows では参照された expert のページが常駐して空き RAM を食い潰すため、PC のフリーズにつながりました。
現在は expert を含めて**その時点の空き RAM の予算内**に収まる配置だけを選び、収まらないモデルは選択肢から外します
(`models.moe_ram_overcommit` で以前の挙動に戻せますが、推奨しません)。メモリ逼迫時は、RAM を多く使うモデルから
VRAM に収まるモデルへ途中で切り替え、手の空いた大きいモデルは解放します。

## 応答モード (v1.8)

利用者が選ぶのは 3 つだけです。Dynamic Profile はそれぞれの範囲の中で、混雑・VRAM/RAM・タスク内容に応じて調整を続けます。

| モード | 内部チューニング t | 動き |
|---|---|---|
| 速度特化 (`fast`) | ≤ 0.2 | 軽いモデル、計画・検証なし、必要なときだけ調査 |
| 精度特化 (`quality`, 既定) | ≥ 0.75 (固定) | 高性能モデル (混雑時も待つ)、調査して根拠付きで回答、検証あり |
| 自律特化 (`autonomous`) | ≥ 0.9 (固定) | 計画 → 調査・実行 → 検証 → 修正を最大 16 ステップ / 30 ツール / 20 分。質問なら出典付きレポート (Deep Research)、作業ならワークスペースで実行まで |

API の `auto` / `deep` は互換のため残しています (`deep` は自律特化の調査レポート)。


## 完全版 Python サンドボックス (v1.10)

`run_code` は、準備ができていれば **Pyodide (CPython 3.13 の WebAssembly 版)** を **Deno** 内で実行します
(pydantic の mcp-run-python / LangChain Sandbox と同じ構成)。numpy / pandas / matplotlib / scipy / scikit-learn /
Pillow / sympy / networkx / statsmodels などが使えます。

- 初回起動の約20秒後にバックグラウンドで取得 (Deno・Pyodide は npm 公式配布物、パッケージは Pyodide の CDN)。
  すべてハッシュ検証。完了するまでは従来の WASM 版 (標準ライブラリのみ) で動き、完了後は再起動なしで切り替わります。
- 作業フォルダはメモリ上にコピーされ、終了時に変更ファイルだけ書き戻します。`plt.show()` だけで保存されなかった
  グラフは自動で `figure.png` として保存し、利用者に表示します。
- 設定: `sandbox.full_python` / `sandbox.python_packages` / `sandbox.backend` (auto / pyodide / wasm)。

## 次世代ワークフロー: データ分析 (Code Interpreter 方式)

グラフ・集計・統計・金利計算などの依頼や CSV / Excel の添付を検出すると (`needs_analysis`)、`run_code` と
作業フォルダを渡し、最低6ステップ・8回のツール実行を確保します。モデルには
「確認 → 計算は必ずコードで → グラフは savefig → エラーは直して再実行 → 要約」の手順を指示し、
実行に失敗したときはツール結果に修正のヒント (使えるパッケージ一覧・タイムアウト時の対処) を付けて自己修復させます。
各実行はチャット上にノートブック風のセル (コード・出力・所要時間) として表示され、会話に保存されます。
調査 (web_research / download_file) と組み合わせれば「調べる → データを取る → 分析する → 図表で答える」まで一続きで動きます。

## モデル戦略: 賢いモデル1つ (v1.10)

`models.strategy = "single"` (既定) では、速度特化・精度特化・自律特化のどれでも
**空きメモリに載る最も賢いモデル1つ**を使い、速度特化は思考の省略と短い出力で速さを出します
(以前は速度特化で 4B の小型モデルに切り替わり、回答の質が急に落ちていました)。
小型モデルを常駐させる設定もこの戦略では無効になり、そのぶんのメモリを大きいモデルに回します。
専門モデル (Coder など) は、高難度のコーディング課題で明確に上回り、かつ別のモデルがロード済みでない場合だけ選ばれます。
小型モデルは「大きいモデルがどうしても載らない」「メモリが危険域 (CRITICAL)」のときの退避先としてだけ使います。
`models.primary_model` で常に使うモデルを固定できます。`adaptive` で従来の動作に戻ります。

これが成り立つ理由は **MoE (Mixture of Experts)**: Qwen3 30B-A3B は 30B 分の知識を持ちながら、1トークンあたり
3B 分しか計算しないため、4B 級の小型モデルとほぼ同じ速度で動きます。

### SSD 直ロードと「無劣化圧縮」について (技術的な限界)

- **SSD を RAM と同じ速さにすることは物理的にできません。** NVMe SSD は約 7〜14 GB/s、DDR5 RAM は約 60〜90 GB/s、
  GPU の VRAM は数百 GB/s 以上です。llama.cpp は既に mmap で SSD から直接読み込んでいますが、生成中に毎トークン
  SSD からモデルを読むと数十倍遅くなります。現実的な最適解は、上記の MoE + 「共有層は VRAM、エキスパートは RAM」
  (`--n-cpu-moe`) で、これは既に実装済みです。
- **精度も速度も一切落とさない「無劣化圧縮」は、現在の GGUF (4bit 量子化済み) にはほぼ効きません。**
  DFloat11 や ZipNN は BF16 (16bit) の重みの指数部の偏りを利用して約 30% 小さくする技術で、出力はビット単位で同一です。
  ただし (1) 元が BF16 なので、30% 縮めても 4bit 量子化版の約 2 倍の大きさ、(2) DFloat11 は CUDA 専用の独自カーネルで
  llama.cpp 非対応、小バッチでは展開処理のぶん遅くなる、(3) 既に量子化された重みは情報がほぼ詰まっているため
  可逆圧縮しても数 % しか縮まない、という理由で、この製品 (12GB 級 GPU + llama.cpp) では採用していません。
  配布・保存時のサイズ削減 (ZipNN) は可能ですが、実行時のメモリは減りません。

## 段階的なモデルの梯子 (v1.11)

文章モデルは「梯子」の段として入れます (カタログの `ladder: {family, tier}`)。

| 段 | モデル | 方式 |
|---|---|---|
| 20B | gpt-oss 20B | MoE (1トークンあたり 3.6B)。最初から MXFP4 (4bit) で学習された「ネイティブ4bit」で、後から量子化した劣化がない |
| 15B | Qwen3 30B-A3B Instruct 2507 REAP-15B | 30B-A3B から、ルーターがあまり使わない専門家を REAP (Cerebras) で半分に剪定。層・注意機構・使う専門家の数はそのままで、知識の多くを保ったまま半分の大きさ |
| 8B | Qwen3 8B | 密モデル |
| 4B | Qwen3 4B Instruct 2507 | 密モデル |

- 段どうしの大きさの比は約2倍以内です。どのセットでも、上の段から一気に最下段へ飛ばないことをテストで保証しています。
- 選び方: まず「RAM へのはみ出しが `models.max_ram_offload_gb` (既定 4GB) を超えるモデル」を外します。12GB GPU では 30B MoE が約8GB はみ出して PC 全体が重くなるため、この規則で外れます。
  次に、直近30分以内に読み込みに失敗したモデルを外します。残りのうち最も賢いモデルを使います (単一モデル戦略)。
- 以前のセットでインストールした PC (4B と 30B だけ) には、起動の約90秒後に足りない段を強い順に1つずつバックグラウンドでダウンロードします。
  ディスクが少ないときは止めます。`models.auto_ladder` で無効化でき、進行状況は管理コンソールのモデル一覧に表示されます。
- 新しい世代のモデルで llama.cpp が「unknown model architecture」で起動に失敗した場合は、最新の llama.cpp を別フォルダに入れて以後の読み込みに使います (6時間に1回まで)。
  その間はすぐ下の段が答えます。
- REAP-15B は有志による変換 (Hugging Face 上の GGUF) です。取得できない場合も他の段は入ります。
  能力値 (`capabilities`) は公開ベンチマークからの推定で、実機の「フル診断」で調整してください。
